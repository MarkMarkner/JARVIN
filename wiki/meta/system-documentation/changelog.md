## 📊 Feedback & Updates

### Wie wird diese Dokumentation aktualisiert?

```
1. Du findest Fehler/Verbesserungen
   → Du sagst mir: "In [Datei] ist Fehler: ..."
   
2. Neue Erkenntnisse während JARVEN-Nutzung
   → Ich aktualisiere relevant Dateien
   → Notation im Changelog: "[2026-MM-DD] [Type] [Change]"
   
3. Architektur-Entscheidungen treffen wir
   → Ich dokumentiere die Entscheidung
   → Implikationen aufzeigen
   → In relevant Datei updaten

4. Monatliche Review (optional)
   → Wir schauen: "Was funktioniert? Was nicht?"
   → Dokumentation anpassen
```

### Update-Kategorien

```
[BUG] — Fehler in der Dokumentation
[CLARIFICATION] — Besser erklären
[NEW FEATURE] — Neue Möglichkeit in JARVEN
[DEPRECATION] — Etwas wird nicht mehr empfohlen
[DECISION] — Neue Entscheidung getroffen
[IMPROVEMENT] — Bessere Praxis gefunden
[INSIGHT] — Neue Erkenntnis nach Nutzung
```

## 🎯 Bekannte Limitierungen dieser Doku

```
1. Sie dokumentiert das System, nicht die Praxis
   → Nach 3 Monaten Nutzung werden wir reale Erfahrungen haben
   → Dann können wir anpassen

2. Sie enthält keine "echten" Beispiele
   → Nur Templates & theoretische Szenarien
   → Nach Ingest von echten Entities wird es konkreter

3. Sie ist nicht interaktiv
   → Du kannst sie nicht "üben"
   → Nur lesen & verstehen

4. Sie behandelt Mark OS noch nicht praktisch
   → Das kommt später, wenn Mark OS existiert
   → Jetzt nur: "Wie JARVEN vorbereiten für Mark OS"
```

## 💡 Erkenntnisse beim Schreiben

### Was gut funktioniert im System

```
✅ 8 Seitentypen sind präzise & ausreichend
   → Keine Ambiguität, welcher Typ wann

✅ Frontmatter-Standard ist gut
   → Strukturiert jede Seite richtig

✅ Folder-Hierarchie ist logisch
   → sources/, entities/, concepts/, questions/

✅ Provenance Ledgers sind durchdacht
   → Tracking von Evidence & Claims funktioniert

✅ Transaction Model schützt vor Inkonsistenz
   → Alles in einer Transaktion = sicher
```

### Was unklar/offen ist

```
⚠️ Seitentyp "task" — Sollte es einen geben?
   → Aktuell: Project-Subtype, aber könnte eigenständig sein
   → Braucht Entscheidung mit dir

⚠️ Zeitliche Dimensionen — Wie Version tracking?
   → Snapshots? Ledger-Metadaten? Git nur?
   → Braucht Entscheidung für Audit-Trail

⚠️ Skalierung — Wann wird es kritisch?
   → Bei 1000 Entities? 10.000?
   → Sollten wir proaktiv planen?

⚠️ Automation — Wo zeichnen wir die Linie?
   → Boundaries definieren ist gut, aber was ist realistisch?
   → Nach Praxis evaluieren
```
